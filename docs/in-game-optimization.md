# 游戏内优化（Phase 5 的实施方案）

## 为什么是"游戏内"而不是"我们的渲染器"

这不是权衡判断，是被测量定下来的。见 `docs/beauty-guided-generation.md` 2026-07-20 那节：

| | |
| --- | --- |
| `beauty(我们的渲染)` vs `beauty(游戏渲染)`，34 角色 × 10 视角 | Spearman ρ = **+0.006** (p=0.97) |
| **天花板**：游戏 vs 游戏自己（两组不相交视角） | **+0.935** |

天花板排除了"指标又坏了"——同一套流程能检出 0.935 的自一致性，所以那个零是真的。

而且这一轮修了耳朵、眨眼、相机（游戏侧原本放大 27%）、走样、镜面，还移植了完整
`BRDF1_Unity_PBS`，**ρ 从 −0.24 走到 +0.01，等于没动**。所以"继续提升保真度直到它能当替身"
这条路有强反证。

**可导渲染器没有作废**，只是不该用在这里。它仍然是以下场景的正确工具：批量几何、对参数求梯度、
以及 `src/face_metrics/` 的面部比例度量（走骨骼世界坐标，不经过像素）。

## CMA-ES 是什么，为什么选它

**Covariance Matrix Adaptation Evolution Strategy** —— 无梯度的连续参数优化器。

维护一个多元高斯 `N(m, σ²C)`，每代：

1. 采样 λ 个候选（这里是 λ 组 59 维滑块）
2. 各评估一次（**只要分数，不要梯度**）
3. 用最好的若干个更新：**均值 m**（往好的区域移动）、**协方差 C**（学习哪些方向重要、
   参数之间如何相关）、**步长 σ**（自适应缩放）

**C 是精髓**：它在没有导数的情况下等价于学出一个局部二阶模型。面部参数彼此强相关
（下巴宽度 × 脸型、眼距 × 眼睛大小），逐坐标搜索在这种病态问题上很吃亏。

### 适配性

| 条件 | 我们的情况 |
| --- | --- |
| 无梯度 | ✅ 游戏是黑箱 |
| 维度适中 | ✅ 59 维在甜区（协方差 59² ≈ 3.5k 个数） |
| 目标有噪声 | ✅ 噪声 sd **0.024** vs 全向量扰动信号 **0.107**（S/N 4.5×）。注意：加视角**压不动**这个地板，只能重复整轮再平均 |
| 评估成本中等 | ✅ 约 1.3 s/次，能跑几千次 |

### 备选方案与不选的理由

- **随机搜索 / 爬山**：59 维下收敛慢一个量级，且不学参数相关性
- **贝叶斯优化**：适合评估**极贵**（≤几百次）的场景；59 维对 GP 偏高，而我们评估便宜——用它是把优势用反
- **有限差分梯度**：59 维每步要 60 次评估才估一个梯度；同样预算下 CMA-ES 能采 60 个点**并**学到协方差结构

## ⚠️ 动手前必须先做的：批量设置滑块

> **2026-07-20 勘误。** 本节原先写的 1.3 s/评估（其中滑块 1.1 s、渲染 0.12 s、打分 0.1 s）
> **是错的，实测差 4 倍**。真实分解（`src/hs2_ingame_eval.py::timing()`，v0.15.0 bridge）：

| 环节 | 原文声称 | **实测** | 占比 |
| --- | --- | --- | --- |
| 设 59 个滑块 | 1.1 s | **2.57 s**（43.5 ms/次往返 × 59） | 50% |
| 渲 5 视角 + 1 张取景探针 | 0.12 s | **0.60 s**（约 100 ms/张） | 12% |
| **打分** | **0.1 s** | **2.02 s**（mtcnn 181 ms + DINOv2 75 ms，每视角） | **39%** |
| 合计 | 1.3 s | **≈ 5.1 s** | |

原因仍然成立：`/maker/face/shapes` **一次只能设一个**，而且 `ApplyFaceShape` 每设一个就调用一次
`UpdateShapeFaceValueFromCustomInfo` + `UpdateShapeFace`，等于**把整张脸重建 59 遍**。
批量端点同时消掉往返和重复重建。

**打分是第二大项，而且不可压缩**（见下节"对齐敏感性"）。批量端点落地后单次评估约 **1 s**，
1200 次评估 ≈ 20 分钟。

**所以第一步仍然是给 bridge 加 `POST /maker/face/shapes/batch`**，一次传 59 个值；
顺带 `/maker/render?yaws=a,b,c` 让 K 个视角共用一次 hide/freeze/settle。

### 对齐敏感性：为什么打分这 2 秒省不掉

mtcnn 占打分的 71%，很自然想到"相机是固定取景的，把对齐变换缓存下来"。**实测否决**：
同一角色 60 组不同滑块扰动下，用首次检测的变换 vs 每次重新检测，两组分数
**Spearman 仅 +0.15**，|差| 均值 0.052（噪声地板的 2 倍）。缓存对齐不是加速，是**换了个量在测**，
而 ρ=0.88 是用逐次检测验证的。

⚠️ 由此还得到一条必须记住的方法论限制：**mtcnn 的相似变换会归一化掉整体脸部尺度和 roll**。
所以"只改变整体头部大小"的滑块会被测出 |ΔS| ≈ 0 —— 不是它对人不重要，而是**测量把它去掉了**。

## 目标函数

单纯最大化 beauty 会把滑块推到 0/1 的轨上，出来是个怪物。必须带 trust region：

```
maximize   S(p) − λ‖p − p₀‖²

S(p) = mean over K≥4 viewpoints of  beauty(game_render(p))
p₀   = 原角色的参数
```

### 每一项的来由

- **K ≥ 4**：单视角 reward 的 ρ 只有 0.479（不可用）；K=4 → 0.859，K=5 → 0.880。
  单视角优化会去拟合渲染噪声，而**分数照样上涨、看起来像成功**。
- **λ**：不该由我定死。应当**跑一条 Pareto 前沿**（不同 λ 对应"改动多大 / 变好多少"）交给用户挑。
- **约束**：滑块夹在 [0,1]。注意 SliderUnlocker 卡可能存越界值，
  而 bridge 端点拒绝写 [0,1] 之外——这些滑块应**冻结**（它们梯度本来也恒为 0，
  关键帧表在端点外是常数）。

### 采集协议（不可省）

游戏渲染对**完全没变化**的角色都曾不可复现（sd 0.139）。必须：

```
hide_hair=1 & freeze_pose=1 & settle=3
+ 每次载入卡片后丢弃第一轮打分
+ 每次参数变化后用 aligned_framing() 重算取景
```

### ⚠️ 噪声地板是 0.024，不是 0.010（2026-07-20 勘误）

本文档原先写"噪声地板 sd ≈ 0.010"。**10 次重复实测是 0.024**（`scripts/hs2_noise_decomposition.py`）。
早先 3 次重复得到 0.0125 是抽样太少——8 次重复的 range 达 0.11。逐层分解：

| 层 | 结果 |
| --- | --- |
| **A 打分器**：同一个 PNG 打 10 次 | sd = **0.000000**，完全确定 |
| **C 取景**：`aligned_framing()` 调 10 次 | `ortho_size` sd = **0.000000**，target sd ~0.0017 |
| **B 渲染**：取景字节级固定，同一 yaw 拍 10 次 | 像素平均偏差仅 **0.206** 灰阶，但分数 sd = **0.0245** |
| **D 完整协议** | sd = 0.0192 |

所以噪声既不来自打分器，也不来自取景，而是**渲染本身的亚像素几何抖动**：热力图显示变化
全部集中在**边缘**（轮廓、眼睑、唇线、雀斑纹理），最大单像素偏差 112 灰阶。

两条要命的性质：

1. **它不随视角平均下降。** 单视角 sd 0.0245，5 视角均值 sd 0.0236 —— 几乎没降。
   独立噪声应降到 0.011。说明抖动在**一轮内的各视角之间是同向的**，不是视角噪声。
   这不推翻多视角（ρ 从 0.479→0.880 是跨角色排名的可靠性，另一回事），但意味着
   **想压这个地板只能重复整轮评估再平均，不能靠加视角。**
2. **等不掉。** settle 扫 3/10/30/60 帧，sd 在 0.015–0.037 之间无趋势。

### 但对 CMA-ES 而言信号是够的

单滑块 ±0.15 的筛查得出 median |ΔS| = 0.039、54/57 低于 2σ，看起来毫无希望。
**这个结论不能外推**——一次只动一个滑块是最弱的探针。按 CMA-ES 实际操作的尺度重测：

| 扰动（全向量，57 个可写滑块） | 分数 sd | 范围 | vs 地板 0.024 |
| --- | --- | --- | --- |
| σ = 0.15 | **0.107** | 2.43 – 2.80 | **S/N 4.5×** |
| σ = 0.30 | **0.133** | 2.40 – 2.81 | **S/N 5.5×** |

**推论：不要用单滑块筛查去冻结维度**（那会冻掉 54/57，等于扔掉整个搜索空间）。
`scripts/hs2_optimize_ingame.py` 因此默认 `--sensitivity ''`，只排除**无法写入**的越界滑块。

⚠️ **越界滑块**：SliderUnlocker 保存的卡会有 [0,1] 之外的值（测试卡上 `[23]=-0.471`、
`[49]=+1.804`）。bridge 端点拒写这些值，所以它们必须**冻结且永不回写**——否则连恢复 p₀ 都会失败。

## 离散部分（化妆贴图选择）

梯度到不了贴图 ID。空间大小实测：

| | |
| --- | --- |
| 各类别选项的**积** | 6.9 × 10¹⁴ —— 穷举没戏 |
| 各类别选项的**和** | **276** —— 坐标下降的单轮代价 |

按类别：`fo_head` 4、`ft_skin_f` 49、`ft_detail_f` 19、`st_eyebrow` 27、`st_eyelash` 9、
`st_eyeshadow` 44、`st_eye` 30、`st_eyeblack` 8、`st_eye_hl` 45、`st_cheek` 17、`st_lip` 19、
`st_mole` 5。

**方法：贪心坐标下降，不用连续松弛。** 松弛（softmax 混合贴图 + 梯度 + 取整）会产生
**游戏做不出的图像**，松弛最优点可能不可实现，取整后落点没有保证——DARTS 的经典失效模式。
和只有 276 时，逐坐标**精确枚举**优于处处近似。

### 两个必须处理的陷阱

1. **先测敏感度再搜索——但用对基准。** 噪声地板是 **0.024**（不是曾经写的 0.109，也不是 0.010）。
   离散搜索和连续搜索在这一点上**不同**：贪心坐标下降**本来就是逐坐标**评估的，所以
   "整个取值范围都低于地板的类别应剔除"在这里是成立的——不像连续部分那样属于欠功效推断
   （见上文"但对 CMA-ES 而言信号是够的"）。预判瞳孔高光、eyeblack 这类占像素极少的多半是平的，
   但**必须测，不能猜**。
   ⚠️ 由于地板**不随视角平均下降**，想把它压到 0.01 只能**重复整轮评估再平均**（4 轮 → 0.012），
   代价是 4×。
2. **winner's curse。** 从 27 个带噪选项取最大值，其期望**必然**高于真实最优——你会看到
   分数上升，但那部分是选择偏差。胜出者必须**重复整轮评估**（不是加视角，见上）复评，
   并与现任做**配对比较**，不能直接信那个 max。

## ⚠️ 可靠性 ≠ 有效性

ρ=0.88 说明 reward 对同一角色给出**稳定**排序，**不**说明这个排序符合人的审美。
它仍然是一个在真人照片上训练的模型在看游戏渲染；多视角平均消除的是**噪声**，不是**偏差**。

**优化产出必须过人眼复核。** 在目标域收标注仍然是证明有效性的唯一手段——只是不再是
动手前的阻塞项。

## 实施顺序

1. bridge：`POST /maker/face/shapes/batch`（4× 加速，先做）
2. `scripts/hs2_optimize_ingame.py`：目标函数 + 采集协议 + CMA-ES 循环（`pip install cma`）
3. 小规模验证：1 张卡、少代数，确认分数确实上升且**游戏内截图肉眼变好**
4. Pareto 前沿：扫 λ，产出"改动幅度 vs 分数增益"曲线交给用户挑
5. 离散搜索：先测每类别敏感度 → 砍平的 → 贪心坐标下降（带 winner's curse 修正）
6. 人眼复核
