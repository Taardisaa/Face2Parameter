# 游戏内优化（Phase 5 的实施方案）

## 为什么是"游戏内"而不是"我们的渲染器"

这不是权衡判断，是被测量定下来的。见 `docs/beauty-guided-generation.md` 2026-07-20 那节：

| | |
| --- | --- |
| `beauty(我们的渲染)` vs `beauty(游戏渲染)`，34 角色 × 10 视角 | Spearman ρ = **+0.006** (p=0.97) |
| **天花板**：游戏 vs 游戏自己（两组不相交视角） | **+0.935** |

天花板排除了"指标又坏了"——同一套流程能检出 0.935 的自一致性，所以那个零是真的。

而且这一轮修了耳朵、眨眼、相机（游戏侧原本放大 27%）、走样、镜面，还移植了完整
`BRDF1_Unity_PBS`，**ρ 从 −0.24 走到 +0.01，等于没动**。所以"继续提升保真度直到它能当替身"
这条路有强反证。

**可导渲染器没有作废**，只是不该用在这里。它仍然是以下场景的正确工具：批量几何、对参数求梯度、
以及 `src/face_metrics/` 的面部比例度量（走骨骼世界坐标，不经过像素）。

## CMA-ES 是什么，为什么选它

**Covariance Matrix Adaptation Evolution Strategy** —— 无梯度的连续参数优化器。

维护一个多元高斯 `N(m, σ²C)`，每代：

1. 采样 λ 个候选（这里是 λ 组 59 维滑块）
2. 各评估一次（**只要分数，不要梯度**）
3. 用最好的若干个更新：**均值 m**（往好的区域移动）、**协方差 C**（学习哪些方向重要、
   参数之间如何相关）、**步长 σ**（自适应缩放）

**C 是精髓**：它在没有导数的情况下等价于学出一个局部二阶模型。面部参数彼此强相关
（下巴宽度 × 脸型、眼距 × 眼睛大小），逐坐标搜索在这种病态问题上很吃亏。

### 适配性

| 条件 | 我们的情况 |
| --- | --- |
| 无梯度 | ✅ 游戏是黑箱 |
| 维度适中 | ✅ 59 维在甜区（协方差 59² ≈ 3.5k 个数） |
| 目标有噪声 | ✅ 噪声 sd 0.010 vs 信号 0.077；多视角平均还能压 |
| 评估成本中等 | ✅ 约 1.3 s/次，能跑几千次 |

### 备选方案与不选的理由

- **随机搜索 / 爬山**：59 维下收敛慢一个量级，且不学参数相关性
- **贝叶斯优化**：适合评估**极贵**（≤几百次）的场景；59 维对 GP 偏高，而我们评估便宜——用它是把优势用反
- **有限差分梯度**：59 维每步要 60 次评估才估一个梯度；同样预算下 CMA-ES 能采 60 个点**并**学到协方差结构

## ⚠️ 动手前必须先做的：批量设置滑块

实测单次评估 ≈ 1.3 s，其中：

| 环节 | 耗时 | 占比 |
| --- | --- | --- |
| **设 59 个滑块** | **1.1 s** | **85%** |
| 渲 5 个视角 | 0.12 s | 9% |
| 打分 | ~0.1 s | 8% |

原因：`/maker/face/shapes` **一次只能设一个**（实测 18.9 ms/次往返 × 59）。

按默认种群 λ = 4+3·ln(59) ≈ 16、300 代 ≈ 4800 次评估：

- 现状：约 **105 分钟**
- 加一个批量端点后：约 **25 分钟**（4×，改动很小）

**所以第一步是给 bridge 加 `POST /maker/face/shapes/batch`**，一次传 59 个值。

## 目标函数

单纯最大化 beauty 会把滑块推到 0/1 的轨上，出来是个怪物。必须带 trust region：

```
maximize   S(p) − λ‖p − p₀‖²

S(p) = mean over K≥4 viewpoints of  beauty(game_render(p))
p₀   = 原角色的参数
```

### 每一项的来由

- **K ≥ 4**：单视角 reward 的 ρ 只有 0.479（不可用）；K=4 → 0.859，K=5 → 0.880。
  单视角优化会去拟合渲染噪声，而**分数照样上涨、看起来像成功**。
- **λ**：不该由我定死。应当**跑一条 Pareto 前沿**（不同 λ 对应"改动多大 / 变好多少"）交给用户挑。
- **约束**：滑块夹在 [0,1]。注意 SliderUnlocker 卡可能存越界值，
  而 bridge 端点拒绝写 [0,1] 之外——这些滑块应**冻结**（它们梯度本来也恒为 0，
  关键帧表在端点外是常数）。

### 采集协议（不可省）

游戏渲染对**完全没变化**的角色都曾不可复现（sd 0.139）。必须：

```
hide_hair=1 & freeze_pose=1 & settle=3
+ 每次载入卡片后丢弃第一轮打分
+ 每次参数变化后用 aligned_framing() 重算取景
```

噪声地板由此降到 **sd ≈ 0.010**。见 `scripts/hs2_local_gradient_agreement.py` 的 docstring。

## 离散部分（化妆贴图选择）

梯度到不了贴图 ID。空间大小实测：

| | |
| --- | --- |
| 各类别选项的**积** | 6.9 × 10¹⁴ —— 穷举没戏 |
| 各类别选项的**和** | **276** —— 坐标下降的单轮代价 |

按类别：`fo_head` 4、`ft_skin_f` 49、`ft_detail_f` 19、`st_eyebrow` 27、`st_eyelash` 9、
`st_eyeshadow` 44、`st_eye` 30、`st_eyeblack` 8、`st_eye_hl` 45、`st_cheek` 17、`st_lip` 19、
`st_mole` 5。

**方法：贪心坐标下降，不用连续松弛。** 松弛（softmax 混合贴图 + 梯度 + 取整）会产生
**游戏做不出的图像**，松弛最优点可能不可实现，取整后落点没有保证——DARTS 的经典失效模式。
和只有 276 时，逐坐标**精确枚举**优于处处近似。

### 两个必须处理的陷阱

1. **先测敏感度再搜索。** 噪声地板 0.109（K=5 时 0.243/√5）。**整个取值范围都低于地板的类别
   应直接剔除**，否则是在拟合噪声。预判瞳孔高光、eyeblack 这类占像素极少的多半是平的，
   但**必须测，不能猜**。
2. **winner's curse。** 从 27 个带噪选项取最大值，其期望**必然**高于真实最优——你会看到
   分数上升，但那部分是选择偏差。胜出者必须**用更多视角重新评估**，并与现任做**配对比较**，
   不能直接信那个 max。

## ⚠️ 可靠性 ≠ 有效性

ρ=0.88 说明 reward 对同一角色给出**稳定**排序，**不**说明这个排序符合人的审美。
它仍然是一个在真人照片上训练的模型在看游戏渲染；多视角平均消除的是**噪声**，不是**偏差**。

**优化产出必须过人眼复核。** 在目标域收标注仍然是证明有效性的唯一手段——只是不再是
动手前的阻塞项。

## 实施顺序

1. bridge：`POST /maker/face/shapes/batch`（4× 加速，先做）
2. `scripts/hs2_optimize_ingame.py`：目标函数 + 采集协议 + CMA-ES 循环（`pip install cma`）
3. 小规模验证：1 张卡、少代数，确认分数确实上升且**游戏内截图肉眼变好**
4. Pareto 前沿：扫 λ，产出"改动幅度 vs 分数增益"曲线交给用户挑
5. 离散搜索：先测每类别敏感度 → 砍平的 → 贪心坐标下降（带 winner's curse 修正）
6. 人眼复核

## 依赖

- `pip install cma`（纯 Python，轻量）
- 游戏运行 + Character Maker 打开
- bridge ≥ v0.15.0（当前已装）
