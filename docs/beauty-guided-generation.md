# Beauty-guided param generation — 设计讨论 (brainstorm)

> **状态:探索中 / 未定案** (dumped 2026-07-18)。这是一次思路讨论的记录,供后续慢慢考虑,
> 不是已确定的实现方案。

## 目标

现在有两套模型:

- **face2param**(`predict.py` / `Face2Param`):图片 → 205 维 param,**忠实**重建一个匹配输入脸的
  游戏角色。但"忠实" ≠ "好看":它只保证像,不保证 beauty score 高。
- **beauty_score**(`beauty_score.py`,本次新增):图片 → beauty 分数 [1,5]。**假设**先把它当作
  我们的评分模型(reward model),暂时不纠结 OOD。

**想做的事:** 把两者拼成一条 pipeline,用 reward model 去引导,让 face2param 生成**分数更高**的
param,而不只是贴近人脸特征的 param。本质上是"**在保持像本人的前提下,生成最好看的那版 param**"——
一个 similarity ↔ beauty 的权衡(一个 λ 旋钮)。

经验证据:输入图在图空间被美化后,face2param 的产出确实更漂亮(实测某微调图 4.1 > 原图 3.7,gap 小
但方向对)。

## 核心难点:reward 打分的是「图」,head 吐的是「param」

- beauty_score 的输入是**图片**(图 → DINOv2 → 分数)。
- head 产出的是 **param**。
- 要给 param 打分,必须先**渲染**成角色图(HS2ABMX 写卡 → 出图),再喂 reward。
- **渲染器是不可导黑盒**,梯度无法从 `param → 渲染 → 分数` 倒流回 head。

"冻结全部、只训一层"的思路本身没问题,**卡的就是这条梯度**。

## 三条路线

### A. 可导「代理 reward」(推荐)
离线学一个小网络 `S(param) → beauty`,逼近"渲染+打分"黑盒。beauty 项就可导了,"加一层 head、其余
冻结"直接能训:

```
L = λ·‖refined − base‖²  +  (1−λ)·( −S(refined) )
        保持像本人             把分数往高推
```

- **关键红利:代理训练数据几乎白嫖。** 现有 `data/cards` 就是"已渲染角色图 + 已知 param"的配对;
  拿 beauty_score 把每张卡图打一遍,立刻得到成千上万条 `(param, beauty)`,**不用新渲染**就能训 S。
  (feature/param/beauty 三者在 card 数据集上天然对齐。)
- **风险:reward hacking** —— head 会钻 S 的漏洞,把 param 推到"S 说好看、真渲染出来其实丑"的区域。
  缓解:① trust region(强约束 refined 别离 base 太远);② 迭代一两轮——把 head 新产出真渲染、
  重新打分、再更新 S(即带学习型奖励模型的离线 RL)。

### B. 黑盒 RL / 进化策略
REINFORCE 或 CMA-ES,直接拿"渲染+打分"当黑盒 reward 更新那层 head。不用代理,但**每次评估都要真
渲染**,HS2ABMX 出图秒级 → 几千次 = 几小时到几天。做小 demo 行,规模化太重。**一般不建议。**

### C. 绕开渲染器:图空间先美化,再走现有 face2param(最省事,已有正向证据)

```
输入图 → (在 DINOv2/ArcFace 空间里,约束身份不变地把 beauty 往上推)
       → 更好看的图 → 现有 face2param → 更好看的 param
```

- beauty 和 face2param 都直接吃**图**,梯度在图空间是通的,**没有不可导渲染器问题**,不用新加 head,
  **无 reward-hacking 风险**。
- 代价:改的是"输入长相"而非直接优化 param head;身份保持要靠约束(可复用项目已有的 `arcface`
  身份 backbone 做 identity 相似度约束)。

> **注:** 路线 A/B 都依赖一个能吃 param 的渲染器——这一环的深入调研(逆向游戏渲染 recipe、
> 可导渲染器)见 [offline-renderer-research.md](offline-renderer-research.md)。一个**可导** offline
> 渲染器能让 `param → 渲染 → 图 → beauty` 全程可导,直接溶解本文的核心难点。

## 关于用户提的架构

"**face2param 后面挂一层 MLP、冻结其余、只训这层、平衡 similarity 与 beauty**" —— **成立,就是路线 A
的形态**。唯一要补的,是让 beauty 变可导的**代理 S**;补上它,架构原封不动就能训。

## 一句实话:OOD 会回来找你

reward-hacking 与 OOD 会**叠加**:拿一个"没见过二次元"的 reward 去优化"渲染出来的二次元角色"。
4.1 vs 3.7 的小 gap 很可能落在 OOD 噪声里。机制能跑通,但"**分数更高 = 人眼更好看**"最终取决于 reward
model 在**渲染角色这个域**上到底准不准。真正的 OOD 解法是:在**目标域(游戏/二次元脸)收一批 beauty
标注**去校准 / 微调 reward(靠迁移不靠谱)。相关背景见记忆 `anime-input-failure-mode`。

## 建议 & 开放问题

- **建议先做路线 C**:复用现有一切、已有正向证据、成本低,先确认"图空间美化 → 更漂亮 param"闭环成立。
- **若坚持把 beauty 焊进 param head 本身**,再上路线 A(代理数据几乎白嫖,架构就是设想的样子)。
- 开放问题:
  1. similarity 项怎么定义最稳?param 空间 L2 vs 渲染图的 ArcFace 身份相似度(后者又要渲染)。
  2. λ 取值 / 是否要一条 Pareto 前沿(不同 λ 给用户挑)。
  3. 代理 S 的迭代闭环要跑几轮才收敛、reward-hacking 到什么程度就停。
  4. OOD:要不要先花力气在目标域收标注,再谈优化——否则优化的是一个不可信的信号。

## 2026-07-19 · 实测:开放问题 4 有答案了 —— reward 在渲染域上不可用

上面第 4 条("OOD:要不要先花力气在目标域收标注")不再是开放问题。用 50 张真实游戏卡
(`E:\HoneySelect2_ArcticFox\UserData\chara\female`,48 张成功)在**游戏自身的渲染**上测了三轮,
复现见 `scripts/hs2_baldness_ablation.py` / `scripts/hs2_scorer_stability.py`。

### 测了什么

原本要回答的是"秃头渲染会不会毁掉美观排序"(计划里的 1 号风险)。梯度上升不需要 reward *准*,
只需要它**单调**,所以指标定成 Spearman ρ 而不是分数差。

| 实验 | 两张图的唯一差别 | Spearman ρ |
| --- | --- | --- |
| 秃头消融 | 有头发 / 无头发 | **0.117** (p=0.43) |
| **控制组** | 都有头发,**只转 3°** | **0.484** (p=5e-4) |

控制组是关键:3° 旋转肉眼几乎看不出来,却已经把排序打乱一半。所以 0.117 主要**不是**头发造成的,
**是打分器在渲染域上本身就是噪声**。原来的秃头风险评估问错了问题。

### 根因不是预处理,也不是随机性

- 打分器**完全确定性**(同图两次 3.525927 / 3.525927)。
- 关掉 mtcnn、改用固定中心裁切,ρ **没有变好**(控制组 0.484→0.401,秃头组 0.117→0.191)
  → 不是对齐抖动。

DINOv2 特征层面的直接测量给出了原因:

| 余弦距离 (1 − cos) | 值 |
| --- | --- |
| 同一角色,3° 扰动(**噪声**) | 0.0036 |
| **不同角色之间**(**信号**) | 0.0088 |

48 张卡的渲染在 DINOv2 空间里挤成一个极窄的锥(不同角色间 cos = 0.9912)。**噪声是信号的 41%。**
特征几乎分辨不出这些角色 —— 对模型来说它们都是"某种 3D 渲染的脸";MLP 头再把这点微小差异
放大成 0.3 的分数波动。这与已知的"真人照片可用、动漫图不可用"是同一个失效模式。

### 结论(对路线的影响)

1. **Phase 5 按原计划不可行**,但**不是因为渲染器不够真**。渲染器的几何/合成/光照都已对上游戏
   (合成贴图 PSNR 26.2 dB、色调差 0.8%)。继续修眼白、BRDF、0.8257、泪膜 **完全不解决这个问题** ——
   这些工作的收益上限被 reward 的 ρ≈0.48 卡死。**因此这些 fidelity 项应当降级,不该是下一步。**
2. 真正的瓶颈是 **reward 不迁移**。可选方向:
   - (a) 在**目标域**收标注(游戏渲染的人工评分)重训/微调 reward —— 唯一从根上解决的做法,贵;
   - (b) 换一个在渲染域上稳的信号(如身份/属性度量),放弃"美观"这个直接目标;
   - (c) 先验证特征提取器:DINOv2 在渲染域上动态范围就不够,换 backbone 或加渲染域自监督可能是前置条件。
3. **在 ρ 提上来之前不要做端到端优化。** 现在做只会让优化器去拟合渲染噪声,而且因为分数确实会上升,
   看起来还像是成功的。

### 补测:多视角平均把 reward 从"不可用"拉回"可用"(同日)

上面诊断出病因是**视角噪声**。视角相关的噪声会平均掉,角色真实的美观度不会 —— 所以对 K 个
视角的分数取平均,nuisance 标准差降 √K 而信号不变。这是唯一直接打击已测病因的做法。

**测法(避免循环论证):** 每个角色拍 2K=10 个偏航角,拆成**两组不相交**的视角集(交错取角度,
避免两组在姿态上系统性不同),问"A 组 K 视角均值"与"B 组 K 视角均值"的排序一致性。
K=1 正好复现原来的单视角测量,整条曲线可比。46 个角色,复现:
`scripts/hs2_multiview_reward.py`。

| K | ρ |
| --- | --- |
| 1 | **0.479** (与原测量 0.484 吻合) |
| 2 | 0.641 |
| 3 | 0.763 |
| 4 | **0.859** |
| 5 | **0.880** |

Spearman–Brown 可靠性公式 `ρ_K = K·ρ₁/(1+(K−1)·ρ₁)` 由 ρ₁=0.479 预测 K=5 为 0.821,实测 0.880
略优 —— 说明噪声**确实**是可平均掉的视角噪声,不是巧合。外推到 ρ=0.95 约需 **20 个视角**。

**⚠️ 这修的是可靠性,不是有效性。** ρ=0.88 说的是"reward 对同一角色给出稳定排序",**不是**
"这个排序符合人的审美"。一个模型可以稳定地错 —— 它仍然是真人照片上训练的模型在看游戏渲染。
多视角平均消除了**噪声**,没有消除**偏差**。所以:

- Phase 5 的**噪声**障碍解除,可以开始做端到端优化(每步渲 K≥4 个视角求平均)。
- **有效性仍未验证。** 优化跑出来的"更美"结果必须送人眼复核;在目标域收一批标注仍然是
  唯一能证明 reward 有效的手段,只是不再是**动手前的阻塞项**。

上文 2026-07-19 那节的结论"Phase 5 按原计划不可行"据此**修正**为:单视角不可行,K≥4 的
多视角平均可行,但结论仅限可靠性。

## 2026-07-20 · 渲染器能不能当 reward 的替身?(结论:目前不能)

Phase 5 的计划是优化 `param → 我们的渲染 → beauty`。但 reward 的可靠性(ρ=0.88, K=5)是在
**游戏渲染**上建立的。两者只有在"reward 对我们的图和对游戏的图给出一致排序"时才是同一个问题。

### 跨角色测试:不一致 (`scripts/hs2_renderer_as_proxy.py`)

同一批 40 个角色、同样 10 个视角、**背景取自游戏截图的中位边缘色**(排除呈现差异):

| | Spearman ρ |
| --- | --- |
| 整帧 | **−0.239** (p=0.14) |
| 紧脸部裁切(去掉脖子/肩) | **+0.194** (p=0.23) |

两者都与 0 无法区分。**均值差 −0.43 是无害的常数偏移**(梯度上升不看绝对值);致命的是**排序无关**:
游戏认为最好看的角色,我们可能排在中间或垫底。优化器会找到让**我们的渲染器**打高分的参数,
而这些参数塞回游戏可能毫无改善 —— 且分数会涨得很好看。

去掉脖子让 ρ 翻正,说明"我们只渲悬浮头、游戏渲半身"是**已证实的**贡献因素之一,但不是全部。

### 局部测试才是优化真正依赖的性质 (`scripts/hs2_local_gradient_agreement.py`)

跨角色排序回答的不是优化提的问题 —— 梯度上升从不比较角色 A 和角色 B,它只扰动**一个**角色
然后问"这一下有没有变好"。两个渲染器完全可能全局排序不一致(系统性的每角色偏移就会导致),
但**局部方向一致**。所以真正该测的是:

> 扰动一张卡的滑块,`Δ_ours` 与 `Δ_game` 是否同向?

Δ 是对同一基线、同一组视角的**配对差分**,视角噪声是共模的,会抵消 —— 这让局部测试远比绝对分敏感。

**1 张卡 / 40 次扰动 / σ=0.10:** ρ = **+0.326** (p=0.04),符号一致率 **45%**(50% = 抛硬币)。
仍然不足以引导优化,但不是零。

### 这个测试逼出来的三个方法论陷阱(比结果本身更值得记)

**① 游戏渲染对一个「完全没变化」的角色都不可复现。**
不写任何参数、连续打分 4 次:3.7414 → 3.8582 → 3.9470 → 3.8554。而我最初测到的"扰动效应"
是 +0.202 —— 也就是说**大部分根本不是扰动造成的**。

| 协议 | sd | spread |
| --- | --- | --- |
| 显示头发,无预热 | **0.139** | 0.371 |
| 隐藏头发,无预热 | 0.039 | 0.109 |
| **隐藏头发 + 丢弃首帧** | **0.008** | — |

原因(用户确认):**头发物理持续摆动** + **待机轻微晃动** + **腹部呼吸**;首帧则是 load/写参数后
角色**尚未稳定**。即使隐藏头发,同一视角连续两次渲染**像素也不逐位相同**。
→ **任何游戏渲染测量都必须:`hide_hair=1` + 丢弃首帧。** 待办:在 bridge 里冻结 Animator
(`speed=0` 并 `Play(state, layer, 0f)` 倒回固定相位)彻底消除,与欠着的 `BakeMesh` 取景修复合并部署。

**② 写入路径本身会移动分数。** 把**完全相同的值**经 POST 再写一遍,分数漂移 **+0.146**。
排查后确认不是 POST 触发了滑块夹取(POST 一个滑块后 59 个值一个没变),而是上面那条时间不稳定性。

**③ 夹取会把扰动系统性推向「平均脸」。** `clip(base+δ, 0, 1)` 在靠近轨的滑块上非对称:
滑块到 0.5 的平均距离从 0.1816 降到 0.1658(约 9%)。而"平均即好看"是审美模型的强效应 ——
这会制造一个**假的正向效应**。→ 越界滑块必须冻结,不能夹。

**④ SliderUnlocker 卡的越界值 bridge 写不回去。** 本测试卡有 5 个滑块(index 27/29/36/38/42)
落在 [0,1] 之外;游戏加载卡片时照单全收,但 `/maker/face/shapes` 端点校验 [0,1] 拒绝写入。
若对它们扰动,游戏会被夹到 1.0 而我们的渲染器用真值 —— **两边参数不同,配对比较直接失效**。
已冻结这些滑块;无损失,因为关键帧表在端点外是常数,它们梯度恒为 0。

### 顺带修正的两处速度结论

一度报告"我们的渲染器比游戏慢 5.7 倍",**错的**。profile 后:

| 一次 K=5 评估 | |
| --- | --- |
| **我们** | **83 ms**(形变 8.2 + 渲染 5×15.0) |
| 游戏 | 120 ms(24 ms/视角) |

我们**快 1.4 倍**,且这是 batch=1;形变批处理后 **0.07 ms/样本**(batch=128)。
之前那个 121 ms 是 `deform()` 不传参时 `from_card()` **每次启动 HS2ABMX.exe 重新解析卡片** ——
优化循环传的是张量,根本不走这条路,我 benchmark 了一个现实中不存在的调用方式。

### 结论

- **渲染器保真度回到关键路径上**,而且有了量化验收标准(proxy ρ ≥ 0.75 / 局部 ρ ≥ 0.7),
  不再是"看着像就行"。之前"因 reward 被 ρ≈0.48 卡死所以降级着色"的论证,在多视角平均解除该上限后
  已经失效,方向甚至相反 —— 我们与游戏的每一处系统性差异,都是优化器可钻的空子。
- 待修(按已证实/嫌疑排序):**脖子与上半身几何**(唯一有实证)、睫毛 premultiplied 混合、
  皮肤着色(half-Lambert → 完整 Unity Standard BRDF + translucency)、眼白。
- **替代路线:直接用游戏当渲染器做黑箱优化**(CMA-ES)。构造上有效,无替身间隙;
  59 维不算多、24 ms/视角不算贵,一次完整优化约 30 分钟。代价是不可导且游戏须开着。

### 2026-07-20 补 · 病因其实是**眨眼**,修完后局部 ρ = 0.44

上一节把游戏渲染的不可复现归因为"待机晃动 + 呼吸 + 头发物理"。**看图之后发现主因是眨眼** ——
连续两帧的差异几乎全部集中在眼睛(一帧睁一帧闭),脸的其余部分是全黑的。教训:该看图的时候在算统计量。

bridge v0.13.0 修了两处(`HS2MCP` 仓库 `ceba424` + `9125a55`):

1. **眨眼没被关掉。** 我的守卫写反了 —— `if (blinkWasOn) ChangeEyesBlinkFlag(false)`,只在标志**已经**
   为 true 时才调用,而那正是不需要调的时候。反编译 `ChaControl` 确认该方法同时
   `SetFixedFlags(1)` 钉住控制器**并** `SetOpenRateForce(1f)` 强制睁眼,所以改为无条件调用。
2. **同帧截图拍不到刚设的状态。** 这些设置要经角色自己的 `LateUpdate` 才作用到网格。
   `RenderHead` 改成协程,应用设置后 `yield` 若干帧(默认 3,`settle=` 可调)再测包围盒和渲染。
   这同时消除了 v0.12 里冻结引入的**重新取景**(倒回动画→头移动→`BakeMesh` 包围盒变→相机重framing)。

| 重复截图的平均像素差 | |
| --- | --- |
| 眨眼中(全新角色,不冻结) | **13.8** |

### 干净数据上的局部梯度一致性

| | 脏数据 | **干净数据** |
| --- | --- | --- |
| Spearman ρ | +0.326 | **+0.441** (p=0.004) |
| Pearson r | +0.375 | **+0.532** |
| 去均值符号一致率 | — | **62.5%** |

("原始符号一致率 47.5%"是**误导性指标**:两边 Δ 有系统性均值偏移(游戏 +0.033 / 我们 −0.043),
有偏移时符号一致率必然被压向 50%。去均值后才是方向一致性。)

噪声修正:游戏侧信噪比 sd 0.079 / 0.010 → 可靠性 0.984,**ρ 修正后仍是 0.445** —— 所以 0.44
不是被噪声压低的,是真实水平。

**读数:** 局部方向**确实存在正相关**,但大约一半方差是渲染器特有的。不足以放心地纯靠我们的渲染器
做优化,但也远非无用。→ 务实方案是**混合**:用可导渲染器做梯度上升**提出候选**,再用游戏
(24 ms/视角,构造上有效)**复核与选择**。各用其所长,而不是赌其中一个够好。
